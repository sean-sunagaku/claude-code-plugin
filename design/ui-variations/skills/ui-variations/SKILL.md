# UI Variations

5つの異なるバリエーションで同一画面のUIを**並列生成**し、Pencilで横並び比較する。
各 ui-designer が `mcp__pencil__batch_design` で直接構築するため、5画面が同時に出来上がる。

## 2つのモード

### Mode A: スタイルプリセット
見た目の違い（色・フォント・レイアウト）を軸にした5バリエーション。
12種のプリセットから選択し、同じ情報設計を異なるビジュアルで比較する。

### Mode B: ペルソナ駆動（推奨）
ペルソナの行動パターン・利用シーン・ペインポイントをUI構造・情報設計レベルで反映した5バリエーション。
「誰にとっての最高のUXか」が異なる5つの設計思想を比較する。
見た目だけでなく、**情報の優先順位・導線・CTA配置・機能のグルーピング**が異なる。

**ペルソナファイルやトンマナファイルが存在する場合はモードBを優先提案する。**

## アーキテクチャ

```
リーダー（あなた）
├── V1チーム: v1-designer + v1-reviewer + v1-copywriter
├── V2チーム: v2-designer + v2-reviewer + v2-copywriter
├── V3チーム: v3-designer + v3-reviewer + v3-copywriter
├── V4チーム: v4-designer + v4-reviewer + v4-copywriter
├── V5チーム: v5-designer + v5-reviewer + v5-copywriter
└── affordance-tester（全バリエーション横断で検証）

各 designer が直接 Pencil に書き込む（MCP ツールはサブエージェントでも使用可能）
affordance-tester は全5バリエーション完成後に初見視点で検証
リーダーは見守り + 最終比較レポート
```

## ワークフロー

1. ヒアリング（画面要件、プラットフォーム、ターゲット）
2. ペルソナ・トンマナの読み込み（存在する場合）
3. バリエーション方向の決定（Mode A or B）
4. Pencil キャンバス準備（5フレーム配置）← リーダーが実施
5. 5チーム並列起動（各3エージェント = 計15エージェント）
6. デザイン構築 + チーム内レビュー ← designer が直接 Pencil 操作
7. スクリーンショット取得 + 比較レポート生成
8. クリーンアップ

## Step 1: ヒアリング

以下を確認（不明ならユーザーに質問）:

- **画面**: どの画面を作るか（ログイン、ホーム、設定等）
- **機能要件**: 画面に必要な要素（ボタン、入力欄、リスト等）
- **プラットフォーム**: iOS / Web / 両方
- **ターゲット**: 年齢層、技術レベル
- **既存コード**: あればソースコードを読んで機能を把握
- **制約**: 必須の色、ブランド要件、既存デザインシステム
- **除外スタイル**: 使いたくないスタイル方向

## Step 2: ペルソナ・トンマナの読み込み

以下のファイルを自動検出して読み込む:

### ペルソナファイル
```
docs/personas/personas/persona-*.md
docs/personas/context.md
```

各ペルソナから以下を抽出:
- **行動パターン**: いつ・どこで・どのように使うか（利用時間帯、デバイス、場所）
- **利用シーン**: 何をしたくてアプリを開くか（ジョブ・トゥ・ビー・ダン）
- **ペインポイント**: 現状の不満・課題
- **期待する体験**: 理想のワークフロー
- **技術レベル**: UI の複雑さの許容度

### トンマナファイル
```
.claude/app-tone-manner/*/TONE_MANNER_REPORT.md
docs/tone-manner/*.md
```

トンマナから以下を抽出:
- **カラーパレット**: プライマリ、セカンダリ、ニュートラル、ダークモード
- **タイポグラフィ**: フォントファミリー、スケール、ウェイト
- **ビジュアルスタイル**: 角丸、シャドウ、アイコン、アニメーション
- **ボイス&トーン**: フォーマリティ、語彙、コピーの方向性
- **デザインテンション**: ブランドの核となる矛盾ペア

**ペルソナが存在する場合**: Mode B（ペルソナ駆動）を提案する。
**ペルソナが存在しない場合**: Mode A（スタイルプリセット）で進める。

## Step 2A: スタイル方向の決定（Mode A）

[references/style-presets.md](references/style-presets.md) を参照し、12種のプリセットから5つを選択。
選択基準:
1. 5つが**明確に異なる**スタイル（似たもの同士を避ける）
2. ユーザーのターゲット・用途に**適合**するもの
3. ユーザーが除外指定したスタイルは**除外**

各スタイルについて以下を定義:
- コンセプト名（日英）
- カラーパレット（背景、プライマリ、テキスト、アクセント）
- フォントファミリーとウェイト
- レイアウト方針（余白、角丸、ボーダー）
- トーン（コピーの方向性）

## Step 2B: ペルソナ駆動バリエーションの設計（Mode B）

### 2B-1. ペルソナ → UX要件の抽出

各ペルソナの行動パターンから**具体的なUX要件**を導出する:

| ペルソナの行動 | → | UX要件（情報設計レベル） |
|--------------|---|----------------------|
| 深夜に使う | → | ダークモード必須、目に優しい配色 |
| 朝の限られた時間で使う | → | 前回セッション即再開が最大CTA |
| GitHub連携を重視 | → | 連携ステータスが常に見える配置 |
| チームに共有したい | → | エクスポート/共有ボタンが目立つ |
| 投資家資料を作りたい | → | 資料テンプレートへの導線 |

**重要**: ここで抽出するのは「色や見た目」ではなく**情報の優先順位・導線・CTA配置・レイアウト構造**。

### 2B-2. 5バリエーションの設計思想を定義

推奨構成:

| V | 名前 | 設計思想 |
|---|------|---------|
| V1 | Universal Best | 全ペルソナの共通ニーズを最大公約数で満たすバランス型 |
| V2 | {ペルソナA}フォーカス | ペルソナAの行動パターンに最適化 |
| V3 | {ペルソナB}フォーカス | ペルソナBの行動パターンに最適化 |
| V4 | {ペルソナC}フォーカス | ペルソナCの行動パターンに最適化 |
| V5 | トンマナ純粋実装 | トンマナの忠実な実装。リファレンスデザイン |

ペルソナが2人の場合:
- V1: Universal Best, V2: ペルソナA, V3: ペルソナB, V4: ハイブリッド（A+B最良部分）, V5: トンマナ純粋

ペルソナが1人の場合:
- Mode A に切り替えるか、同一ペルソナの異なる利用シーン（朝 vs 夜等）で分割

### 2B-3. 各バリエーションの詳細設計

各バリエーションについて以下を定義:

**情報設計（Mode A にはない要素）:**
- **最大CTA**: この画面で最も目立たせるアクション（ペルソナの最重要ジョブに直結）
- **情報の優先順位**: 何を上部に、何を折りたたむか
- **サイドバー/ナビの構成**: ペルソナのワークフローに沿った導線
- **セクション配置**: ペルソナの利用シーンに最適化した画面構造
- **特殊要素**: ペルソナ固有の機能（例: GitHub連携ステータス、時間見積もり表示）

**ビジュアルスタイル:**
- カラーパレット（トンマナベース + ペルソナ適応）
- フォントファミリー（トンマナから。ダークモードの場合はウェイト調整）
- レイアウト方針（密度、余白、グリッド）
- トーン（コピーの方向性）

## Step 3: Pencil キャンバス準備（リーダーが実施）

1. `get_editor_state` で現在のファイルを確認
2. `get_guidelines` でデザインガイドライン取得（topic: "web-app" or "mobile-app"）
3. `find_empty_space_on_canvas` で空き領域を特定
4. 5つのルートフレームを横並びに配置:

**iOS の場合:**
```
V1 (gap:100)  V2 (gap:100)  V3 (gap:100)  V4 (gap:100)  V5
393x852       393x852       393x852       393x852       393x852
```

**Web の場合:**
```
V1 (gap:100)  V2 (gap:100)  V3 (gap:100)  V4 (gap:100)  V5
1440x820      1440x820      1440x820      1440x820      1440x820
```

各フレームの設定:
- width/height: プラットフォームに合わせたサイズ
- clip: true
- layout: vertical
- name: "V{N}: {ConceptName}"

**重要**: 各フレームのノードIDを記録する。designer に渡す情報として必須。

## Step 4: チーム作成と16エージェント起動

TeamCreate で `ui-variations` チームを作成。

### タスク作成

TaskCreate で以下を作成:

**バリエーションごと（x5）:**
- `V{N} デザイン構築` - ui-designer 担当
- `V{N} デザインレビュー` - design-reviewer 担当（デザイン構築に blockedBy）
- `V{N} コピー作成` - copy-writer 担当（デザイン構築に blockedBy）

**全体:**
- `V{N} アフォーダンス検証` x5 - affordance-tester 担当（各デザイン構築に blockedBy）
- `スクリーンショット取得 + 比較` - リーダー担当（全タスクに blockedBy）

### エージェント起動

**1つのメッセージで16エージェントを並列起動する。**

各バリエーションにつき3エージェント + 全体1エージェント:

```
subagent_type: "general-purpose"
team_name: "ui-variations"
name: "v{N}-designer" (or v{N}-reviewer, v{N}-copywriter)
model: "opus"
mode: "bypassPermissions"
run_in_background: true
```

**affordance-tester（1体、全バリエーション横断）:**
```
subagent_type: "general-purpose"
team_name: "ui-variations"
name: "affordance-tester"
model: "opus"
mode: "bypassPermissions"
run_in_background: true
```

**注意**: `subagent_type` は `"general-purpose"` を使用する（MCP ツールへのアクセスが必要なため）。
プロンプトに各エージェントの役割定義（agents/*.md の内容）を含める。

### プロンプトに含める情報

**ui-designer へ:**

## Step 5: 進行管理

リーダーの役割:
- 基本は**見守り**。エージェントが自律的に作業
- designer が直接 Pencil に構築 → reviewer がスクショ確認 → copywriter がコピー提案
- 詰まったエージェントがいればアドバイス

### 並行編集の安全ルール

5つの designer が同じ .pen ファイルに同時書き込みする。競合を防ぐため:
- 各 designer は**自分の割り当てフレーム内のみ**操作する
- 他の V{N} フレームへの Insert/Update/Delete は禁止
- `document` への直接 Insert は禁止（リーダーのみ）
- reviewer/copywriter は読み取り専用（`get_screenshot`, `batch_get` のみ）、書き込みは designer が行う
- プロンプトに「あなたの担当フレームID: {nodeId}」を必ず明記する

チーム内フロー:
1. ui-designer が `mcp__pencil__batch_design` でデザイン構築
2. ui-designer が `mcp__pencil__get_screenshot` で確認
3. ui-designer が reviewer と copywriter に完成通知
4. design-reviewer が `mcp__pencil__get_screenshot` でレビュー → フィードバック
5. copy-writer が `mcp__pencil__get_screenshot` でデザイン確認 → コピー提案
6. ui-designer が修正 → 最終版をリーダーに報告

## Pencil テクニカルノート

designer のプロンプトに必ず含める:

- テキストの色は `fill` プロパティ（`textColor` は無効）
- `justifyContent` は `space_between`（アンダースコア、ハイフンではない）
- `batch_design` は最大25操作/コール
- Insert は必ずバインディング名が必要: `foo=I("parent", {...})`
- Copy した子ノードの更新は `descendants` プロパティ経由
- 画像は `G()` 操作（AI生成 or stock）
- 画像は frame/rectangle に fill として適用（image ノード型は無い）
- `filePath` パラメータは毎回必ず指定する
