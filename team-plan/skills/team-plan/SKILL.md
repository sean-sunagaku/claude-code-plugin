# Team Plan

実装タスクを受け取ったとき、**まず並列に Explore エージェントでコードベースを調査**し、
その調査結果をもとに **Plan Mode で実装計画を作成**してからユーザーの承認を得て実装する。
「調べてから作る」というシンプルな原則で、影響範囲の見落としや手戻りを防ぐ。

## ワークフロー概要

```
タスク分析（調査観点を決定）
  → Task(Explore) 並列起動（2〜5体）
  → 全エージェントの結果を待つ
  → 調査結果を統合
  → EnterPlanMode
  → 実装計画を作成
  → ExitPlanMode（ユーザー承認を求める）
  → ユーザーが承認したら実装開始
  → ユーザーが修正を求めたら EnterPlanMode に戻る
```

---

## Step 1: タスク分析と調査観点の決定

タスクを受け取ったら、以下の6カテゴリから「このタスクに必要な観点」を選ぶ。
**選んだ観点の数 = Explore エージェントの数**（最低2体、最大5体）。

### 調査カテゴリ一覧

| # | カテゴリ | 調査する内容 |
|---|----------|------------|
| 1 | 既存実装の把握 | 変更対象のファイル・クラス・関数がどこにあるか |
| 2 | 依存関係とインターフェース | 変更対象が何に依存し、何から依存されているか |
| 3 | テストの現状 | テストファイルの構造・テスト方法・カバレッジ状況 |
| 4 | 類似実装・パターン | コードベース内の参考になる実装・命名規則 |
| 5 | 設定・環境 | ビルド設定・環境変数・設定ファイルの構造 |
| 6 | ドキュメント・コメント | README・既存コメント・型定義 |

### タスク種別ごとの推奨観点

- **バグ修正** → カテゴリ 1, 2, 3
- **新機能追加** → カテゴリ 1, 2, 4, 5
- **リファクタリング** → カテゴリ 1, 2, 3, 4
- **設定変更** → カテゴリ 5, 6
- **不明・複合** → カテゴリ 1, 2, 4（デフォルト3体構成）

---

## Step 2: Explore エージェントを並列起動

選択した各観点に対して、Task(subagent_type="Explore") を **1つのメッセージ内で並列に** 起動する。
全エージェントを同時に呼び出すこと（逐次起動は非効率なので禁止）。

### 技術的制約（必ず把握する）

- **Explore が使えるツール**: Glob, Grep, Read, WebFetch, WebSearch のみ
- **Write/Edit/Bash/Task は使えない**: 調査結果はファイル保存せず、コンテキストに返す
- **並列上限**: 同時10体まで（通常は3〜5体が現実的なコスト範囲）
- **ネスト不可**: Explore から Task を呼ぶことはできない

### 起動パラメータ

```
subagent_type: "Explore"
run_in_background: false   # 全員の結果をコンテキストに返してから統合するため
```

### 各エージェントへのプロンプト構造

以下のテンプレートを観点ごとに埋めて使う:

```
あなたは「{カテゴリ名}」の専門調査員です。
以下のタスクに関連して、コードベースを調査してください。

## 調査対象
{ユーザーから受け取ったタスクの概要}

## 作業ディレクトリ
{現在の作業ディレクトリの絶対パス}

## 調査観点
{単一の観点を明確に記述}

## スループネスレベル
medium  # 通常はこれ。広い調査なら very thorough、軽い確認なら quick

## 調査手順
1. {具体的な検索クエリ／ファイルパス}
2. {追加検索戦略}

## 重要: 正確性の担保
- パターン検索（Grep/Glob）で候補を見つけたら、必ず Read でファイルの該当箇所を実際に読み、現在の実装状態を確認すること
- 「〜が存在しない」「〜が未実装」と報告する場合は、該当ファイルを Read で確認した上で断言すること
- 推測や仮定ではなく、ファイルの実際の内容に基づいて報告すること

## 出力形式（この形式で返すこと）
## {カテゴリ名} 調査結果
### 発見した内容
{自由記述}
### 重要なファイル・パス
- {絶対パス}: {内容の説明}
### 実装への示唆
- {箇条書きで、実装者が知っておくべきこと}

## 成功基準
[カテゴリ名] に関して実装判断に必要な情報が揃ったら完了。
```

### カテゴリ別の調査ポイント例

**カテゴリ1: 既存実装の把握**
- 変更対象の関数・クラス・モジュールが定義されているファイルを探す
- 現在の実装の概要（行数・依存ライブラリ・主要なロジック）

**カテゴリ2: 依存関係とインターフェース**
- 変更対象を import/require しているファイルを全て列挙
- 変更対象が export しているシンボルと、その使われ方

**カテゴリ3: テストの現状**
- テストファイルの場所（`*.test.*`, `*.spec.*`, `__tests__/` など）
- テストフレームワークの種類と実行方法（package.json の scripts）
- 変更対象に関連するテストケースの概要

**カテゴリ4: 類似実装・パターン**
- コードベース内で類似の実装を探す（Glob・Grep を活用）
- 命名規則・ファイル配置のパターン
- 参考にすべき実装例とそのパス

**カテゴリ5: 設定・環境**
- ビルド設定ファイル（tsconfig.json, webpack.config.js, vite.config.ts など）
- 環境変数の定義（.env ファイル、設定オブジェクト）
- パッケージ管理（package.json の dependencies / devDependencies）

**カテゴリ6: ドキュメント・コメント**
- README.md の関連セクション
- 変更対象周辺の JSDoc / TSDoc コメント
- 型定義ファイル（.d.ts）の内容

## Step 3: 調査結果の統合

全 Task(Explore) の返り値を受け取った後、以下の手順で統合する。

1. **重要ファイルの一覧化**: 各エージェントが報告した「重要なファイル・パス」を重複排除して一覧にする
2. **実装への示唆を整理**: 「変更対象」「注意点」「参考パターン」の3カテゴリに分類する
3. **矛盾の解決**: 情報が矛盾する場合は、より具体的な情報（ファイルパス付き・行番号付き）を優先する
4. **「未実装」「存在しない」報告の検証**: エージェントが「〜がない」と報告した場合、統合前に Grep/Read で自分でも確認する。偽陰性（実際にはあるのに「ない」と報告）を防ぐ
5. **統合サマリーの作成**: 次の Plan Mode で使う内部メモとして整理する（ユーザーへの表示は不要）

統合サマリーの構造（内部メモ用）:
```
## 調査統合サマリー
### 変更対象ファイル
- {絶対パス}: {役割}
### 注意すべき依存関係
- {ファイルA} は {ファイルB} に依存（変更時は影響確認が必要）
### 参考にすべきパターン
- {ファイルC}: {どんなパターンの参考になるか}
### テスト状況
- {テストファイルのパス}: {何をテストしているか}
```

## Step 4: Plan Mode で実装計画を作成

調査結果の統合が完了したら、**EnterPlanMode** を呼び出す。

### 4a: 事前検証（Plan Mode 内で実施）

Plan Mode に入ったら、計画を書く **前に** 変更対象ファイルの該当箇所を Read で直接確認する。
Explore の調査結果を鵜呑みにせず、「本当に変更が必要か」「既に実装されていないか」を検証する。

- 変更対象ファイルの該当行を Read で確認
- 調査結果と現在のファイル内容に矛盾がないか検証
- 矛盾がある場合は調査結果を修正してから計画を書く

### 4b: 計画の作成

Plan Mode 内で以下の構造の計画を書く:

```markdown
## 実装計画

### 調査で判明した前提・制約
- 既存構造の概要（変更対象ファイルと役割）
- 注意すべき依存関係（変更の影響が波及するファイル）
- テストの現状（既存テストの場所と実行方法）

### 変更対象ファイル一覧
| ファイル | 変更内容 |
|---------|---------|
| {絶対パス} | {何をどう変えるか} |

### 実装ステップ（順序付き）
1. {具体的なステップ（何のファイルの何を変えるか）}
   - 挿入位置の目印: {前後のコード・コメント・関数名など、行番号ではなくコンテキストで特定}
2. {次のステップ}
3. ...

> **Note**: 行番号は参考として使ってよいが、実装時は必ず Read でファイルを再確認すること。
> Explore の調査と実装の間にファイルが変更される可能性がある。

### テスト計画
- {実装後に確認すること}
- {実行すべきテストコマンド}

### リスク・注意点
- {変更による予期しない影響の可能性}
- {注意して扱うべき箇所}
```

計画を書き終えたら **ExitPlanMode** を呼び出し、ユーザーに計画の承認を求める。

---

## Step 5: ユーザー承認後の実装

### 承認された場合

実装を開始する。以下のガイドラインに従う:

- **実装前に必ずファイルを再読み込みする**: Explore の調査結果には行番号が含まれるが、調査から実装までの間にファイルが変更されている可能性がある。**編集対象のファイルは Edit の直前に必ず Read で最新内容を取得**し、old_string に使う文字列を目視確認すること
- **行番号ではなくコンテキスト（周辺コード）で編集位置を特定する**: 行番号は参考情報に留め、Edit ツールの old_string には十分な周辺コンテキストを含める（前後の関数名・コメント・ブロック構造など）
- 計画通りのステップで実装する
- **計画外の変更が必要になった場合**: 即座にユーザーに報告し、続けてよいか確認する
- 各ステップ完了後に簡潔に進捗を報告する（例:「ステップ1完了: {ファイル名} を変更しました」）
- エラーが発生した場合は原因を分析し、計画の見直しを提案する

### 修正を求められた場合

**EnterPlanMode** に戻り、ユーザーのフィードバックをもとに計画を更新する。
更新後は再び **ExitPlanMode** でユーザーの承認を求める。

---

## 注意事項

- **並列起動を徹底する**: Explore エージェントを逐次起動してはいけない。常に1メッセージで全員を同時起動する
- **Plan Mode を省略しない**: 調査結果があっても、必ず EnterPlanMode → ExitPlanMode を経由してユーザーの承認を得る
- **観点は動的に決める**: 全6カテゴリを常に使うのではなく、タスク内容に応じて必要な観点だけを選ぶ

### 探索フェーズのスキップ条件

以下の条件を **すべて** 満たす場合は Step 2（Explore 起動）をスキップして Step 4（EnterPlanMode）に進んでよい:

- 変更対象のファイルパスがユーザーから明示されており、他のファイルへの影響が明らかにない場合
- 単一ファイル内の 1〜3 行の変更（コメント追加・typo 修正・定数値の変更など）

それ以外のケースでは必ず Step 2 を実行する。「簡単そうだから」という主観的な判断でのスキップは禁止。

### その他の制約事項

- **Explore はファイル保存できない**: Write が使えないため調査結果はコンテキストに返す（`run_in_background: false`）
- **Plan Mode 内で Task/Skill は呼べない**: EnterPlanMode 後は Glob/Grep/Read/WebFetch/WebSearch のみ利用可能
- **エージェント数はコストを意識して選ぶ**: 1体あたり約20,000トークン。3〜5体が現実的な上限
