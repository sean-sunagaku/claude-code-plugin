# 外部リサーチ & スキル連携

---

## ドメインドキュメント連携

各ステップ開始時、`docs/domain/` 配下のドキュメントを読み込み、議論を既存仕様に接地させる。

1. `Glob`で `docs/domain/*.md` を検索
2. ユーザーが言及した画面・機能に関連するドキュメントを読み込む
3. 読み込んだ内容を全エージェントにコンテキストとして渡す
4. エージェントはドメインドキュメントの内容を前提として議論する

**NG**: ドキュメントに書いてある仕様をユーザーに質問する
**OK**: ドキュメントを前提に、その先の判断をユーザーに質問する

---

## 競合・業界リサーチ

Step 2（代替案）で `WebSearch` を使い、議論を外部知見で補強する。
内部知識だけに閉じず、競合アプリや業界ベストプラクティスを参照して議論の幅を広げる。

### リサーチタイミング

- **Step 2 開始時**（必須）: Engineer のコードベース調査と並列で実行
- **議論中**（任意）: エージェントが「業界ではどうしているか知りたい」と判断した場合

### リサーチ手順

1. **競合アプリの特定**: ユーザーの機能要望に関連する競合アプリを `WebSearch` で検索
   - 検索例: `"[機能名] app UI pattern"`, `"[機能名] best practice UX"`
2. **実装パターンの調査**: 競合がどう実装しているかを調査
   - 検索例: `"[アプリ名] [機能名] how it works"`
3. **業界ベストプラクティス**: UX/UI のベストプラクティスを調査
   - 検索例: `"[機能カテゴリ] UX best practice 2025"`, `"[UIパターン名] design pattern"`

### リサーチ結果の活用

```
# Engineer と並列でリサーチエージェントを起動
Task(
  description="Research: competitive analysis",
  subagent_type="general-purpose",
  prompt=`
    以下の機能について、競合アプリと業界ベストプラクティスを調査してください。

    機能: [機能概要]
    課題: [Step 1 の課題定義]

    調査項目:
    1. この機能を持つ競合アプリ（3つ以上）の実装方法
    2. UX/UIの業界ベストプラクティス
    3. よくある失敗パターン

    出力フォーマット:
    ### 競合アプリの実装例
    | アプリ名 | 実装方法 | 強み | 弱み |
    |---------|---------|------|------|

    ### 業界ベストプラクティス
    - [パターン名]: [説明]

    ### よくある失敗パターン
    - [パターン名]: [なぜ失敗するか]
  `
)
```

リサーチ結果は全エージェントにコンテキストとして渡し、代替案の提案・評価に活用する。

## 次スキル連携

各ステップの成果物は、他のスキルの入力として活用できる。
セッション完了時、またはステップ完了時に、次に使うべきスキルを提案する。

```
┌─────────────────────────────────────────────────────────────┐
│                  Feature Discussion                         │
│                                                             │
│  Step 1 ─── Step 2 ─── Step 3 ─── Step 4 ─── Step 5       │
│  課題深掘り   代替案     スコープ    要件定義    UI設計       │
│                                                             │
└──────┬──────────┬──────────┬──────────┬──────────┬──────────┘
       │          │          │          │          │
       ▼          │          │          ▼          ▼
  ┌─────────┐     │          │   ┌───────────┐  ┌────────────────┐
  │ /jtbd   │     │          │   │/team-plan │  │/frontend-design│
  │ /5-whys │     │          │   │ 実装計画   │  │ UI実装         │
  └─────────┘     │          │   └───────────┘  └────────────────┘
                  ▼          ▼
           ┌───────────┐  ┌───────────────┐
           │/devils-   │  │/pre-mortem    │
           │ advocate  │  │ リスク分析     │
           └───────────┘  └───────────────┘
```

**ステップごとの連携先**:

| 完了ステップ | 連携先スキル | 用途 |
|------------|------------|------|
| Step 1 完了 | `/jtbd` | ユーザーの本質的な動機をさらに深掘り |
| Step 1 完了 | `/five-whys` | 課題の根本原因を特定 |
| Step 2 完了 | `/devils-advocate` | 選定案の追加批判 |
| Step 3 完了 | `/pre-mortem` | MVPのリスク事前分析 |
| Step 4 完了 | `/team-plan` | 要件定義 → 実装計画を作成 |
| Step 5 完了 | `/frontend-design` | UI設計プロンプト → 実装 |
| Step 5 完了 | `/ui-variations` | 複数UIバリエーションを生成・比較 |

**提案フォーマット**:
```
━━━━ 次のアクション ━━━━

このステップの成果物を活かして、以下のスキルに進めます：

  📋 /team-plan    → 要件定義をもとに実装計画を作成
  🎨 /frontend-design → UI設計プロンプトで画面を実装

どれに進みますか？（または「次のステップ」で Step <N+1> へ）
```

# Mode B: プロダクト機能設計

## リサーチ資料の自動読み込み

Mode B ではセッション開始時に、過去のリサーチ成果物を自動検出・読み込みする。
これにより、議論が既存のリサーチデータに接地される。

### 検出パス

| 資料 | 検索パス | 必須/任意 |
|------|---------|----------|
| ペルソナ | `docs/personas/*.md`, `.claude/personas/*.md` | **必須** |
| 競合分析 | `docs/competitive-analysis/*.md`, `COMPETITIVE_ANALYSIS_REPORT.md` | **必須** |
| プロダクトコンテキスト | `docs/product-context.md`, `product-context.md` | **必須** |
| トンマナ | `docs/tone-manner/*.md`, `TONE_MANNER_REPORT.md` | 任意（あれば反映） |
| 市場調査 | `docs/market-research/*.md`, `MARKET_RESEARCH_REPORT.md` | 任意（あれば反映） |
| ユーザージャーニー | `docs/user-journey/*.md` | 任意（あれば反映） |

### 読み込みフロー

```
1. Glob で各検索パスを探索
2. 必須資料が見つからない場合 → ユーザーに案内:
   「競合分析が見つかりません。先に /competitive-analysis を実行してください」
3. 見つかった資料を読み込み、各エージェントにコンテキストとして配布
4. 任意資料が見つかった場合 → 追加コンテキストとして配布
5. session.json の researchSources に読み込みパスを記録
```

### 読み込み結果の表示

```
━━━━ リサーチ資料読み込み ━━━━
  ✅ ペルソナ: 3件（田中太郎、鈴木花子、佐藤次郎）
  ✅ 競合分析: 1件（5社分析済み）
  ✅ プロダクトコンテキスト: 1件
  ✅ トンマナ: 1件（ブランドアーキタイプ: Explorer）
  ⚠️ 市場調査: なし（議論に影響なし、後で追加可能）
  ⚠️ ユーザージャーニー: なし（議論に影響なし、後で追加可能）
```

## 競合・業界リサーチ（Mode B）

Mode B の Step P2（機能アイデア発想）では、Mode A よりも広範なリサーチを実施する。

### リサーチ対象

1. **競合アプリの機能一覧**: 各競合が持つ機能を網羅的にリスト（既存の競合分析レポートを補完）
2. **カテゴリトレンド**: App Store / Google Play のカテゴリ内トレンド
3. **異業種の参考例**: 同じ課題を別の方法で解決しているアプリ
4. **UXパターン**: オンボーディング、習慣形成、エンゲージメントの業界ベストプラクティス

### リサーチ手順

```python
# Step P2 と並列で実行
Task(
  description="Research: 機能ベンチマーク",
  subagent_type="general-purpose",
  prompt=`
    以下のプロダクトの機能アイデア発想を支援するため、業界リサーチを実施してください。

    プロダクト: [概要]
    カテゴリ: [カテゴリ]
    競合: [競合一覧]
    ペルソナ: [ペルソナ要約]

    調査項目:
    1. 競合アプリの機能一覧（各社の特徴的な機能）
    2. カテゴリ内のトレンド機能（最近追加された新機能）
    3. 異業種の参考例（同じ課題を別アプローチで解決）
    4. オンボーディング・習慣形成のベストプラクティス
    5. ユーザーレビューで頻出する要望（App Store / Google Play）

    出力フォーマット:
    ### 競合の機能マッピング
    | 機能カテゴリ | 競合A | 競合B | 競合C | 差別化機会 |
    |------------|-------|-------|-------|----------|

    ### カテゴリトレンド
    - [トレンド名]: [説明]

    ### 異業種の参考例
    - [アプリ名]: [参考ポイント]

    ### 習慣形成パターン
    - [パターン名]: [説明 + 成功事例]
  `
)
```

│                                                                   │
└──────┬──────────┬──────────┬──────────┬──────────┬───────────────┘
       │          │          │          │          │
       ▼          │          │          ▼          ▼
 ┌──────────┐     │          │   ┌───────────┐  ┌────────────────┐
 │/persona- │     │          │   │/team-plan │  │/ui-variations  │
 │ creation │     │          │   │ 実装計画   │  │ UIバリエーション │
 │ 追加ペルソナ│   │          │   └───────────┘  └────────────────┘

           ┌──────────┐│/feature-     │
           │/devils-  ││ discussion   │
           │ advocate ││ (Mode A)     │
           └──────────┘│ 個別機能壁打ち│
                       └───────────────┘

**ステップごとの連携先（Mode B）**:

| 完了ステップ | 連携先スキル | 用途 |
|------------|------------|------|
| Step P1 完了 | `/persona-creation` | ペルソナが不足していれば追加作成 |
| Step P2 完了 | `/devils-advocate` | 機能候補リストの追加批判 |
| Step P3 完了 | `/feature-discussion` (Mode A) | 個別機能の深掘り壁打ち |
| Step P4 完了 | `/team-plan` | MVP機能の実装計画を作成 |
| Step P5 完了 | `/ui-variations` | 主要画面のUIバリエーションを生成・比較 |
| Step P5 完了 | `/frontend-design` | 画面の実装 |

**Mode B → Mode A の連携**:

Step P4（MVP定義）完了後、個別機能の要件を深掘りしたい場合は Mode A に切り替え可能:

```
━━━━ 次のアクション ━━━━

MVP機能セットが確定しました。以下のアクションに進めます：

  🔍 /feature-discussion → MVP機能を個別に深掘り壁打ち（Mode A）
  📋 /team-plan         → 実装計画を作成
  🎨 /ui-variations     → 主要画面のUIバリエーションを比較

個別機能の壁打ちをする場合は「壁打ち開始：[機能名]」で Mode A に切り替わります。
```
