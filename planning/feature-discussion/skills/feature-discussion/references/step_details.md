# 各ステップの詳細

各ステップの担当エージェント、フロー、完了条件、出力先を定義する。
Mode A（機能壁打ち）は Step 1-5、Mode B（プロダクト機能設計）は Step P1-P5。

---

# Mode A: 機能壁打ち

---

## Step 1: 課題・目的の深掘り

**担当**: PM（リード）+ UX Analyst + Behavioral Psychologist
**目的**: 機能の本質的な価値を明確化

**フロー**:
1. Facilitator がユーザーにヒアリング（課題・目的・動機）
2. PM が課題を構造化し、ビジネス価値を評価
3. UX Analyst がペルソナ視点で「本当にこのペルソナが求めているか？」を批判的に評価
4. **Behavioral Psychologist** がフォッグ行動モデルで評価:
   - 「ユーザーはこの課題を解決する動機が十分か？」
   - 「解決行動を取る能力/容易さはあるか？」
   - 「行動を起こすきっかけは何か？」
5. 3者の意見が対立する場合、全てをユーザーに提示

**PMへの問い**:
- この課題の優先度は？ビジネスインパクトは？
- 解決しないとどうなる？

**UX Analystへの問い**:
- ペルソナ[名前]は本当にこの課題で困っている？
- ペルソナの行動パターンと矛盾しないか？

**Behavioral Psychologistへの問い**:
- ユーザーは「困っている」と言っているが、実際に行動を変えるほど困っているか？
- この課題の解決は習慣化に繋がるか、一回きりか？
- 現状維持バイアスを超えるだけの動機があるか？

**ユーザーに確認すべき事項**:
- この課題に至った背景・きっかけ（なぜ今これが必要だと思ったか）
- 既存の運用やワークアラウンドの有無（今どう対処しているか）
- 想定している利用シーン（いつ・どこで・どんな状況で使うか）
- 優先度の感覚（他の課題と比べてどのくらい重要か）

**完了条件**: 課題と目的が明確化され、ペルソナとの整合性 + 行動実現性が確認された
**出力先**: `1_purpose.md`

---

## Step 2: 代替案・既存機能の検討

**担当**: 全員参加（Engineer: コード調査、Designer: UI案）
**目的**: 新規開発の必要性を検証し、代替案を比較

**フロー**:
1. **Engineer** がコードベースを調査（`Glob`, `Grep`, `Read`で既存実装を把握）
2. **競合リサーチ** を並列で実行（`references/external_research.md` 参照）
3. **Designer** がUI観点から3つ以上の代替案を提示（ASCII artで視覚化）
4. **PM** がビジネス観点で各案を評価
5. **UX Analyst** がペルソナ観点で各案を評価
6. **Behavioral Psychologist** が各案の行動実現性を評価:
   - 「案Aは習慣ループが成立するか？」
   - 「案Bは選択肢が多すぎて選択麻痺を起こさないか？」
   - 「案Cのデフォルト設計は適切か？」
7. **Engineer** がDesignerの案に対して技術的実現性・リスクを反論
8. **Designer** がEngineerの制約に対して代替UIを提案
9. Facilitator が議論を整理してユーザーに提示

**代替案提示フォーマット**:
```
チームで3つの代替案を議論しました：

案A: [概要]
  PM: 工数 [小/中/大]、ビジネス価値 [低/中/高]
  Engineer: 技術的難易度 [低/中/高]、リスク: [...]
  Designer: UIイメージ [ASCII art]
  UX Analyst: ペルソナ[名前]の評価 [...]
  Behavioral Psychologist: 行動実現性 [高/中/低]、懸念: [...]

案B: ...
案C: ...

⚡ チーム内の対立点:
  - [Engineer vs Designer: ...]
  - [PM vs UX Analyst: ...]

推奨: 案[X]（理由: ...）
どれが最も適切だと思いますか？
```

**ユーザーに確認すべき事項**:
- 参考にしているアプリやサービスがあるか
- 既存UIで気に入っている部分・不満な部分
- PC/スマホどちらを主に使うか（利用比率）
- 各案に対する直感的な好み・違和感

**完了条件**: 代替案を3つ以上提示し、チーム議論を経て推奨案を選定
**出力先**: `2_alternatives.md`

## Step 3: スコープ決定（MVP定義）

**担当**: PM（リード）+ Engineer + UX Analyst + Behavioral Psychologist
**目的**: 最小限の実装範囲を決定

**フロー**:
1. **PM** がMVP・Nice to Have・Futureに分類
2. **Engineer** が各項目の技術的工数を見積もり、PMの分類に反論
   - 「PMはMVPと言っているが、技術的に複雑すぎる。Nice to Haveに落とすべき」
   - 「PMはFutureと言っているが、今やらないと後で大幅な改修が必要」
3. **UX Analyst** がペルソナ視点で優先度に反論
   - 「PMはNice to Haveと言っているが、ペルソナ[名前]にとっては必須」
   - 「PMはMVPと言っているが、ペルソナの利用頻度を考えるとFutureでいい」
4. **Behavioral Psychologist** が習慣形成の観点でスコープに反論
   - 「MVPに報酬フェーズが含まれていない。これでは習慣化しない」
   - 「オンボーディングがFutureに分類されているが、初回体験なしに継続利用はありえない」
   - 「フォッグ行動モデルの3要素（動機・能力・きっかけ）がMVPに揃っているかチェック」
5. Facilitator が合意点・対立点を整理してユーザーに提示

**優先度マトリクス**:
```
🔴 MVP（チーム合意）
  - [全員が必須と認めた項目]

🟡 議論中（対立あり）
  - [項目]: PM=[MVP] / Engineer=[Nice to Have]（理由: ...）
  - [項目]: UX=[MVP] / PM=[Future]（理由: ...）

🟢 Future（チーム合意）
  - [全員がFutureで合意した項目]

対立している項目について、どう判断しますか？
```

**ユーザーに確認すべき事項**:
- リリーススケジュールの制約（いつまでに出したいか）
- 開発リソースの制約（自分一人か、チームか）
- MVP に絶対含めたい/含めなくてよいと思う項目
- エージェント間の対立点に対するユーザーの判断

**完了条件**: MVP・Nice to Have・Futureに分類完了（対立はユーザー判断で解決）
**出力先**: `3_scope.md`

---

## Step 4: 要件定義ドキュメント生成

**担当**: UX Analyst（リード）+ PM + Engineer + Behavioral Psychologist（レビュー）
**目的**: ユーザー視点での要件定義書を作成

**フロー**:
1. **UX Analyst** がペルソナベースのユーザーストーリーを作成
2. **PM** が受け入れ条件を定義
3. **Engineer** が技術的実現性の観点からレビュー・反論
   - 「この受け入れ条件は現在のアーキテクチャでは実現困難」
   - 「この操作は既存のAPIでは対応できない」
4. **Behavioral Psychologist** が動機付けの観点からレビュー
   - 「ユーザーストーリーの "So that" は本当に内発的動機か？」
   - 「受け入れ条件に "ユーザーが迷わない" ための要素が含まれているか？」
   - 「初回利用→習慣化のトリガーが要件に含まれているか？」
5. 全員の指摘を受けて修正
6. Facilitator が最終版をユーザーに提示

**出力内容**:
1. 機能概要
2. ユーザーストーリー（As a [ペルソナ名] / I want / So that）
3. 受け入れ条件（Given / When / Then）
4. 行動設計メモ（Behavioral Psychologistによる注意点）
5. チーム内で議論になった点と解決策

**ユーザーに確認すべき事項**:
- ユーザーストーリーの「So that（得られる価値）」がユーザーの意図と合っているか
- 受け入れ条件に漏れがないか（エッジケース、エラー時の振る舞い）
- 非機能要件（パフォーマンス、データ量、同時アクセス）

**完了条件**: ユーザーストーリーと受け入れ条件が全エージェントの合意を得た
**出力先**: `4_requirements.md`

---

## Step 5: UI設計プロンプト生成

**担当**: Designer（リード）+ UX Analyst + Behavioral Psychologist + 全員レビュー
**目的**: UI設計のためのプロンプトを生成

**フロー**:
1. **Designer** が画面レイアウト・インタラクションを提案（ASCII art）
2. **UX Analyst** がペルソナの操作習慣・認知負荷の観点から批判
3. **Engineer** が技術的制約から批判（既存コンポーネントとの整合性）
4. **Behavioral Psychologist** が行動設計の観点から批判:
   - 「デフォルト値が設定されていない → 選択麻痺のリスク」
   - 「初回操作のフィードバックが弱い → 習慣ループの報酬が不足」
   - 「CTAが目立たない → きっかけ（Prompt）が弱い」
   - 「情報量が多すぎる → 認知負荷がワーキングメモリの限界を超える」
5. **Designer** が批判を受けて修正案を提示
6. Facilitator が最終版をユーザーに提示

**出力内容**（各画面について）:
1. 画面の目的
2. レイアウト図（ASCII art）
3. 主要コンポーネント（既存の再利用を優先）
4. ユーザーフロー
5. チーム議論で変更になった点
6. 実装プロンプト

**ユーザーに確認すべき事項**:
- UI案に対する好み・違和感
- 操作フローが自分の想定と合っているか
- デザインのトーン（シンプル志向 vs リッチ志向）

**完了条件**: 画面ごとのプロンプトが全エージェントのレビューを通過
**出力先**: `5_ui_prompt.md`

# Mode B: プロダクト機能設計

---

## Step P1: コンテキスト統合

**担当**: PM（リード）+ UX Analyst + Behavioral Psychologist
**目的**: 全リサーチ資料を統合し、「誰の何を解決するプロダクトか」を全員で合意

**入力資料**:
- product-context.md（プロダクトビジョン・課題仮説・ビジネスモデル）
- competitive-analysis/（競合の強み弱み・差別化ポイント・ERRC）
- personas/（ペルソナプロファイル）
- tone-manner/（ブランドパーソナリティ・デザイン変数）
- market-research/（市場規模・トレンド）
- user-journey/（ユーザー行動パターン）

**フロー**:
1. **PM** がプロダクトビジョンを言語化:
   - 「このプロダクトは[誰]の[何]を[どう]解決する」
   - ビジネスモデルの整理（マネタイズ方法、ターゲット市場）
   - 競合との差別化ポイントの整理
2. **UX Analyst** がペルソナのJTBD（Jobs-to-be-Done）を整理:
   - 各ペルソナが「雇いたいジョブ」を3つ以内に絞る
   - ペルソナ間の共通ジョブと固有ジョブを分類
3. **Behavioral Psychologist** がペルソナの行動パターンから「本当に必要な価値」を抽出:
   - 「ペルソナが言っていること」と「実際にやっていること」のギャップ
   - 行動変容が必要な場合の動機・障壁分析
   - 競合乗り換えの心理的コスト（現状維持バイアス）
4. 3者の視点を統合し、プロダクトの核心的価値を定義

**PMへの問い**:
- このプロダクトの「競合にない価値」は何か？
- ビジネスモデルは持続可能か？

**UX Analystへの問い**:
- 3つのペルソナのJTBDに共通する「核心的ジョブ」は何か？
- 既存ツール（競合含む）ではなぜこのジョブが満たされないのか？

**Behavioral Psychologistへの問い**:
- ペルソナは本当に現状に不満か？現状維持バイアスを超える動機はあるか？
- 競合からの乗り換えコストを上回る価値は何か？

**ユーザーに確認すべき事項**:
- プロダクトの「一言で説明するなら」（エレベーターピッチ）
- 最も重要だと思うペルソナ（優先順位）
- 競合との差別化で最も重視すること
- ビジネスモデルの方針（フリーミアム、サブスク、買い切り等）

**完了条件**: プロダクトビジョン・ペルソナJTBD・競合ギャップ・核心的価値が全員合意で定義された
**出力先**: `P1_context_synthesis.md`

## Step P2: 機能アイデア発想

**担当**: 全員参加
**目的**: ペルソナのJTBD・競合ギャップ・ビジョンから機能候補を網羅的にリストアップ

**フロー**:
1. **PM** がビジネス価値の高い機能を提案:
   - P1で定義したビジネスモデルを実現する機能
   - 競合のERRC（Eliminate/Reduce/Raise/Create）に基づく機能
   - マネタイズに直結する機能
2. **UX Analyst** がペルソナ別に求める機能を提案:
   - 各ペルソナのJTBDを実現する機能
   - ペルソナのフラストレーションを解消する機能
   - 競合で「不満」と言われている機能の改善版
3. **Engineer** が技術的に差別化できる機能を提案:
   - AI/自動化で差別化できる機能
   - 既存技術スタックで効率的に実現できる機能
   - コードベースの既存資産を活用できる機能
4. **Designer** がUX的にインパクトのある機能を提案:
   - 「体験の差」を生む機能（速さ、美しさ、楽しさ）
   - 競合にない新しいインタラクションパターン
5. **Behavioral Psychologist** が習慣形成に必要な機能を提案:
   - Hook Model（トリガー→アクション→可変報酬→投資）の各要素
   - オンボーディング・初回体験に必要な機能
   - 習慣化を阻む機能の排除
6. **Affordance Tester** が初見ユーザーの基本期待を確認:
   - 「このカテゴリのアプリなら当然あると期待する機能」は何か
   - 初見ユーザーが最初に探す機能は何か
7. 全員の提案を統合し、機能候補リストを作成（重複排除、カテゴリ分類）

**機能アイデアリスト提示フォーマット**:
```
チームで [N]個の機能候補が出ました：

■ コア機能（全ペルソナ共通）
  F1: [機能名] — [概要]
      提案: [PM/UX/Engineer] / ペルソナ価値: [高/中] / 競合状況: [差別化/パリティ/キャッチアップ]
  F2: ...

■ ペルソナ特化機能
  F10: [機能名] — [概要]（ペルソナ: [名前]向け）
      提案: [UX] / 差別化度: [高/中/低]

■ 習慣形成・エンゲージメント
  F20: [機能名] — [概要]
      提案: [BP] / Hook Model要素: [トリガー/アクション/報酬/投資]

■ 技術的差別化
  F30: [機能名] — [概要]
      提案: [Engineer] / 実現難易度: [低/中/高]

⚡ 議論ポイント:
  - [機能X]: PMは必要、Engineerは実現困難と主張
  - [機能Y]: UXは必須、PMはROI低と主張
```

**ユーザーに確認すべき事項**:
- リストに含まれていない「絶対欲しい機能」があるか
- 「これは絶対いらない」と思う機能があるか
- 競合の中で「これは真似したい」と思う機能
- 技術的チャレンジを許容するか（AI機能等）

**完了条件**: 全角度からの機能候補がリストアップされ、カテゴリ分類・重複排除された
**出力先**: `P2_feature_ideation.md`

## Step P3: 機能優先度決定

**担当**: PM（リード）+ UX Analyst + Engineer + Behavioral Psychologist
**目的**: 全機能候補を優先度マトリクスで評価・グルーピング

**フロー**:
1. **PM** が Impact/Effort マトリクスを作成:
   - ビジネスインパクト（収益・成長・差別化）をスコアリング
   - 各機能の優先カテゴリ案（Quick Win / Strategic / Nice to Have / Costly）
2. **UX Analyst** がペルソナ価値スコアを算出:
   - 各ペルソナ×各機能の価値スコア（1-5）
   - ペルソナのJTBD達成にどれだけ貢献するか
   - 「全ペルソナに価値がある機能」と「特定ペルソナ向け機能」を明確に
3. **Engineer** が技術的実現性・工数を見積もり:
   - 各機能の工数（楽観/最頻/悲観）
   - 技術的依存関係（Aを作らないとBが作れない）
   - 既存コードベースとの親和性
4. **Behavioral Psychologist** が習慣形成貢献度をスコアリング:
   - Hook Modelの各要素（トリガー/アクション/報酬/投資）への貢献
   - 「この機能がないと習慣化しない」クリティカル機能の特定
   - 行動実現性スコア
5. 全スコアを統合した優先度マトリクスを作成
6. エージェント間で分類の対立を議論

**優先度マトリクス提示フォーマット**:
```
━━━━ 機能優先度マトリクス ━━━━

| # | 機能 | ビジネス | ペルソナ価値 | 技術実現性 | 習慣貢献 | 総合 | カテゴリ |
|---|------|---------|-----------|----------|---------|------|---------|
| F1 | ... | 5 | 4.3 | 4 | 5 | 4.6 | Quick Win |
| F2 | ... | 4 | 5.0 | 2 | 3 | 3.5 | Strategic |

⚡ 分類で対立している機能:
  F5: PM=[Quick Win] / Engineer=[Costly]（理由: 技術的依存が多い）
  F8: UX=[必須] / PM=[Nice to Have]（理由: ROI不明確）

📊 技術的依存関係:
  F1 → F3 → F7（この順序で実装必須）
  F2 → F5（F2完成後にF5着手可能）
```

**ユーザーに確認すべき事項**:
- スコアリング結果に違和感がないか
- 「スコアに関わらず絶対やりたい/やりたくない」機能があるか
- エージェント間の対立についてのユーザー判断
- リリース目標時期とリソース制約

**完了条件**: 全機能にスコアが付き、優先カテゴリに分類され、対立が解消された
**出力先**: `P3_prioritization.md`

---

## Step P4: MVP機能セット定義

**担当**: PM + UX Analyst + Engineer + Behavioral Psychologist + Affordance Tester
**目的**: MVP/Phase2/Phase3 に分類し、各機能の概要要件を定義

**フロー**:
1. **PM** がP3の優先度マトリクスをもとにMVP候補を選定:
   - Quick Win + 高優先Strategic をMVP候補に
   - MVPの機能数は10個以内を目安
   - 「最小限で価値を届ける」を徹底
2. **UX Analyst** が各ペルソナのコアジャーニーがMVPで完結するか検証:
   - 「ペルソナ[名前]がアプリを開いて、主要なジョブを完了できるか？」
   - ジャーニーの途中で「この機能がない」と止まるポイントを特定
   - ペルソナ間の優先度判断（全ペルソナに完璧は不可能、誰を優先するか）
3. **Engineer** が技術的依存関係から実装順序を提案:
   - MVP内の実装順序（依存グラフ）
   - 「この機能をMVPに入れると、他の機能のコストが膨らむ」警告
   - Phase2/3 への先送りが技術的に安全かチェック
4. **Behavioral Psychologist** がMVPで習慣ループが成立するか検証:
   - Hook Model: トリガー→アクション→可変報酬→投資が一通り成立するか
   - フォッグ行動モデル: 動機×能力×きっかけがMVP内で揃うか
   - 「MVPだけでユーザーが定着する」と言えるか
5. **Affordance Tester** がMVP機能セットだけで初見ユーザーが価値を理解できるか検証:
   - 「このアプリは何のためのアプリか」がMVPだけで伝わるか
   - 必要な説明・オンボーディングの要否
6. 全員の評価を統合し、MVP/Phase2/Phase3 を確定
7. MVP各機能について概要要件（1-3行）を定義

**MVP定義提示フォーマット**:
```
━━━━ MVP機能セット定義 ━━━━

■ MVP（リリース1）: [N]機能
  F1: [機能名] — [概要要件1-3行]
  F3: [機能名] — [概要要件1-3行]
  ...

■ Phase 2: [N]機能
  F2: [機能名] — [先送り理由]
  ...

■ Phase 3 / Future: [N]機能
  F10: [機能名] — [先送り理由]
  ...

📊 ペルソナジャーニー検証:
  ペルソナA（拓真）: MVP完結 ✅ / 不足: なし
  ペルソナB（彩）: MVP完結 ⚠️ / 不足: F8（Phase2で補完）
  ペルソナC（隼人）: MVP完結 ✅ / 不足: なし

🔄 習慣ループ検証:
  トリガー: F1の通知 ✅
  アクション: F3の操作フロー ✅
  可変報酬: F5のフィードバック ✅
  投資: ⚠️ Phase2のF8で本格化
  → 判定: 最小限の習慣ループは成立
```

**ユーザーに確認すべき事項**:
- MVPの機能セットで「最低限使えるアプリ」になっているか
- Phase2/3に送る機能で「本当に後でいい」と納得できるか
- ペルソナの優先順位（全員に完璧は無理な場合、誰を優先するか）
- リリース目標との整合性

**完了条件**: MVP/Phase2/Phase3 分類が完了し、MVPの概要要件が定義され、ペルソナジャーニー・習慣ループの検証が完了した
**出力先**: `P4_mvp_definition.md`

## Step P5: 画面構成 & UI設計プロンプト生成

**担当**: Designer（リード）+ UX Analyst + Engineer + Behavioral Psychologist + Affordance Tester
**目的**: 画面マップ・ナビゲーション構造・各画面のUI設計プロンプトを生成

**フロー**:
1. **Designer** が画面マップを作成:
   - MVP全機能を画面に割り当て（1機能=1画面とは限らない）
   - メイン画面・サブ画面・モーダル・設定画面を列挙
   - ナビゲーション構造（タブバー、ドロワー、スタック）を設計
   - 画面遷移図（Mermaid or ASCII art）
2. **UX Analyst** がペルソナ別の導線を設計:
   - ペルソナごとの「最初に見る画面」「主要フロー」
   - ペルソナごとの優先タスクがスムーズに完了できる導線
   - ナビゲーションの情報アーキテクチャ評価
3. **Engineer** が技術的に必要な画面を補完:
   - 認証画面（ログイン、サインアップ、パスワードリセット）
   - 設定画面（アカウント、通知、プラン管理）
   - エラー画面・オフライン対応画面
   - 既存のコンポーネント・ライブラリとの整合性
4. **Behavioral Psychologist** が初回体験フローを設計:
   - オンボーディング（何画面で何を見せるか）
   - 初回利用で「Aha moment」に到達するまでの最短フロー
   - 認知負荷チェック（各画面の情報量が適切か）
5. **Affordance Tester** が認知的ウォークスルーを実施:
   - 画面遷移の自明性（「次にどこを押すか」が分かるか）
   - タブ/メニューのラベルが初見で理解できるか
   - 主要フローの各ステップでユーザーが迷わないか
6. **Designer** が各画面のUI設計プロンプトを作成:
   - レイアウト（ASCII art）
   - 主要コンポーネント一覧
   - インタラクション仕様
   - 実装プロンプト

**画面構成提示フォーマット**:
```
━━━━ 画面構成 ━━━━

■ 画面マップ（[N]画面）
  [タブバー構成]
  ├─ ホーム（F1, F3）
  ├─ [機能名]（F2, F5）
  ├─ [機能名]（F7）
  └─ 設定

■ 画面遷移図
  [Mermaid or ASCII art]

■ ペルソナ別メインフロー
  拓真: ホーム → [画面A] → [画面B] → 完了
  彩:   ホーム → [画面C] → [画面D] → 完了
  隼人: ホーム → [画面A] → [画面E] → 完了

■ 各画面のUI設計プロンプト
  [画面ごとに: 目的、レイアウト、コンポーネント、実装プロンプト]
```

**ユーザーに確認すべき事項**:
- 画面構成・ナビゲーションの好み
- デザインのトーン（トンマナとの整合性確認）
- PC/スマホどちらを優先するか
- 参考にしたいアプリのUI
- 画面遷移図に違和感がないか

**完了条件**: 画面マップ・遷移図が全員合意で完成し、各画面のUI設計プロンプトが全エージェントのレビューを通過した
**出力先**: `P5_screen_architecture.md`
