# 設計実践チェックリスト

設計の各段階で使う判断基準・チェックリスト集。
Step 2〜3 の議論でエージェントが参照する。

---

## SOLID 原則チェックリスト

### SRP（単一責任原則）
「このクラス/モジュールを変更する理由は1つだけであるべき」

チェックリスト:
- [ ] このモジュールを変更する理由は何か？1つか？
- [ ] 複数の「アクター」（ユーザー・管理者・システム等）のニーズに同時に奉仕していないか
- [ ] 「〇〇と△△の両方の責任を持つ」と説明できてしまう場合は SRP 違反の疑い

**判定の問い**: 「誰がこの変更を要求するか？」複数の答えがある → 分割を検討

---

### OCP（開放閉鎖原則）
「拡張に対して開いており、修正に対して閉じているべき」

チェックリスト:
- [ ] 新しいケースを追加する際、既存コードを変更せず追加だけで対応できるか
- [ ] `if/switch` で型・種別を判定しているコードがないか（ポリモーフィズムで代替できる）
- [ ] 振る舞いの追加が「新しいクラスを作る」で完了するか

**典型的な OCP 違反**:
```swift
// 違反: 新しい支払い方法のたびに switch を修正する必要がある
func process(payment: Payment) {
    switch payment.type {
    case .creditCard: processCreditCard(payment)
    case .payPal: processPayPal(payment)
    // 新しい種別追加のたびにここを変更
    }
}

// 準拠: 新しい支払い方法はプロトコルに準拠した新クラスを追加するだけ
protocol PaymentProcessor {
    func process(payment: Payment)
}
```

### LSP（リスコフ置換原則）
「サブタイプはその基底型と置換可能であるべき」

チェックリスト:
- [ ] サブクラス/実装クラスが基底クラス/プロトコルの「契約」を破っていないか
- [ ] 基底クラスの仮定（前提条件・事後条件）をサブクラスが変えていないか
- [ ] 基底クラスを受け取る関数にサブクラスを渡したとき、予期しない動作が起きないか

**典型的な LSP 違反**:
```swift
// 違反: Rectangle を継承した Square が width 設定時に height も変えてしまう
// Square は Rectangle の「幅と高さは独立して設定できる」という契約を破っている
class Square: Rectangle {
    override func setWidth(_ w: Int) {
        super.setWidth(w)
        super.setHeight(w)  // 高さも変える → Rectangle の契約違反
    }
}
```

**実践的な対処**: 継承より合成（Composition over Inheritance）を使う。

---

### ISP（インターフェース分離原則）
「クライアントが使わないメソッドへの依存を強制しない」

チェックリスト:
- [ ] このインターフェース/プロトコルの全メソッドを実装クラスが使うか
- [ ] 実装クラスが「使わないメソッドは例外を投げる」実装をしていないか
- [ ] 大きなインターフェースを小さな役割ごとのインターフェースに分割できるか

**典型的な ISP 違反と解消**:
```swift
// 違反: 読み取り専用クライアントも write メソッドの実装を強制される
protocol DataStore {
    func read(key: String) -> Data?
    func write(key: String, value: Data)  // 読み取り専用クライアントには不要
    func delete(key: String)              // 読み取り専用クライアントには不要
}

// 準拠: 役割ごとに小さなプロトコルに分割
protocol Readable {
    func read(key: String) -> Data?
}
protocol Writable {
    func write(key: String, value: Data)
    func delete(key: String)
}
// 読み取り専用クライアントは Readable のみ依存
```

---

### DIP（依存性逆転原則）
「高レベルのモジュールは低レベルのモジュールに依存してはならない」

（詳細は `module_design_principles.md` の「依存性逆転原則（DIP）」セクションを参照）

チェックリスト:
- [ ] ドメイン層が具体的な実装（DB・フレームワーク等）に直接依存していないか
- [ ] 依存先が「インターフェース/プロトコル」として定義されているか
- [ ] DI（Dependency Injection）でコンストラクタから依存を注入しているか

## 状態管理パターン選択基準

### 状態の種類と推奨パターン

| 状態の種類 | 推奨アプローチ | 理由 |
|-----------|-------------|------|
| 単一コンポーネントのローカル状態 | `useState`, `@State` | シンプルで十分 |
| 親子コンポーネント間 | Props ドリリング or Context | 範囲が限定的 |
| 複数コンポーネントで共有（UI状態） | Context API, Provider | ツールが不要 |
| 複雑なグローバル状態 | Zustand, Jotai, Redux Toolkit | 予測可能性が重要 |
| サーバーから取得するデータ | TanStack Query, SWR | キャッシュ・同期が複雑 |
| iOS の複雑な状態 | TCA | 副作用・テストが重要 |
| iOS の単純な状態 | MVVM + @Observable | 学習コストが低い |

### Repository Pattern（データアクセスの抽象化）

**いつ使うべきか**:
- 複数のデータソースがある（API + ローカルDB + キャッシュ）
- データソースを差し替える可能性がある（MockRepository でテスト）

**チェックリスト**:
- [ ] Repository インターフェースはドメインの言語で定義されているか（SQL文ではなく）
- [ ] キャッシュ戦略は Repository の実装に閉じ込められているか
- [ ] 呼び出し側（UseCase）は Repository がどのデータソースを使うか知らないか

```swift
// 良い例: ドメインの言語
protocol OrderRepository {
    func findById(_ id: OrderID) async throws -> Order  // ドメイン用語
    func findByCustomer(_ customerId: CustomerID) async throws -> [Order]
}

// 悪い例: 技術詳細が漏れている
protocol OrderRepository {
    func executeSQL(_ query: String) -> [[String: Any]]  // SQL詳細が漏れている
}
```

### Unidirectional Data Flow (UDF)

**いつ使うべきか**: 状態が複数コンポーネントで共有され、予測可能性が重要なとき。
**いつ使うべきでないか**: 状態がローカルで単純なとき（YAGNI）。

```
Action → Reducer → State → View → (ユーザー操作) → Action（繰り返し）
```

**チェックリスト**:
- [ ] 状態変化がすべて Action を通じて行われているか（直接 State を変更していないか）
- [ ] Reducer が純粋関数か（副作用を含まないか）
- [ ] 副作用（API 呼び出し・DB操作）が Effect に閉じ込められているか

### CQRS（読み書き分離）

**いつ使うべきか**:
- 読み取りと書き込みのパフォーマンス要件が大きく異なるとき
- 複雑な集計クエリが必要なとき

**いつ使うべきでないか**: シンプルな CRUD アプリ（YAGNI）。

**チェックリスト**:
- [ ] Command（書き込み）側と Query（読み取り）側が独立したモデルを持つか
- [ ] 読み取り専用のクエリモデルが正規化されていなくても問題ないか
- [ ] 結果整合性（Eventual Consistency）を受け入れられるか

### Observer / Event-Driven の注意点

**利点**: モジュール間の疎結合
**リスク**: Event Spaghetti（過剰なイベント連鎖でデバッグが困難になる）

**チェックリスト**:
- [ ] イベントの連鎖が3段階以上にならないか（A→B→C→D は危険信号）
- [ ] イベントの発行元と購読者が追跡可能か（ロギング・デバッグ手段があるか）
- [ ] 同期的に解決できる問題をイベントで非同期化していないか（過剰設計）

## 過剰設計防止チェックリスト（YAGNI / KISS）

### 設計を追加・複雑化する前に問う

- [ ] **今日のユースケースが解決できるか？** 今の要件に存在しない「将来の機能」への対応ではないか
- [ ] **この抽象化のコストを払えるだけの変化頻度があるか？** 変わらないものを抽象化しても意味がない
- [ ] **「将来〜が必要になるかも」という理由だけで追加していないか？** → YAGNI 違反
- [ ] **チームの全員がこの設計を理解できるか？** 新しいメンバーがオンボードできるか
- [ ] **削除するときに他の何かを壊さないか？** 疎結合の確認
- [ ] **テストを書かなければ、この設計が必要か判断できないか？** テストが動機なら正当

### 「シンプルな代替案はないか」チェック

| 複雑な設計 | シンプルな代替 | 複雑な設計が正当化される条件 |
|-----------|-------------|--------------------------|
| インターフェース + 複数実装 | 具体的な実装クラス1つ | 差し替えの実需がある・テストでモックが必要 |
| 複数レイヤー（Service, Repository, Entity） | 単一のクラスに実装 | ビジネスロジックが複雑・チーム規模が大きい |
| Event-Driven + Pub/Sub | 直接メソッド呼び出し | 非同期が必要・モジュール間の疎結合が重要 |
| CQRS | 単一のデータモデル | 読み書きのスケール要件が大きく異なる |
| マイクロサービス | モノリス | チームが複数・独立デプロイが必要 |

### 3の法則（抽象化のタイミング）

```
1回目: そのまま実装する
2回目: 重複に気づくが、まだ待つ（2回の重複は偶然かもしれない）
3回目: 初めて抽象化する

なぜ3回？
→ 2回の重複で抽象化すると、3回目が微妙に違うパターンで
  「間違った抽象化」になりやすい
```

## 段階的アーキテクチャの採用基準

「いつアーキテクチャを複雑化すべきか」の判断基準:

| シグナル | 対応 |
|---------|------|
| テストが書けない（依存を切り離せない） | DIP を適用してインターフェースを導入 |
| 変更が波及範囲が想定より広い | モジュール分割・依存方向を見直す |
| 同じロジックが3箇所以上ある | 3の法則に従って抽象化する |
| 機能追加のたびに既存コードを変更する | OCP を適用してポリモーフィズムで対応 |
| チームメンバーがコードの意図を理解できない | コメント・命名の改善 or モジュール分割 |
| パフォーマンスが実際に問題になった | 計測してから最適化する（推測で最適化しない） |

### 段階的アーキテクチャの推奨アプローチ

```
Step 1: まずシンプルに始める
  → モノリシック、単純な MVC / MVVM

Step 2: 痛みを感じたときに変える
  → テストが困難、変更が広範囲に影響する、チームが大きくなった

Step 3: 最小限のパターンを適用する
  → 問題を解決する最小限のパターンを選ぶ（Clean Architecture 全体ではなく Repository だけでも良い）
```

## プラットフォーム別・状態管理クイックリファレンス

### iOS / SwiftUI
```
状態の複雑さ:
  単純 → @State / @StateObject
  画面間共有 → @EnvironmentObject / @Observable
  複雑な副作用・テスト重視 → TCA
  中程度の複雑さ → MVVM + @Observable + Repository

避けるべきパターン:
  - シングルトンによるグローバル状態（テスト困難）
  - ViewController への過剰なロジック集中（Massive ViewController）
```

### React / Next.js
```
状態の種類:
  ローカル UI 状態 → useState, useReducer
  フォーム状態 → React Hook Form
  サーバーデータ → TanStack Query / SWR
  グローバル UI 状態 → Zustand / Jotai
  過去の負債対応 → Redux Toolkit

Server Component vs Client Component（Next.js App Router）:
  → Server: データフェッチ・SEO・認証・重いコンポーネント
  → Client: インタラクション・ブラウザ API・リアルタイム更新
  → "use client" は本当に必要な場所のみ（末端コンポーネントに閉じる）
```

### Flutter
```
状態管理:
  シンプル → setState / ValueNotifier
  中程度 → Provider / Riverpod
  複雑 → BLoC / Riverpod + AsyncNotifier

推奨:
  現在の主流 → Riverpod（コンパイル時安全性・DI が容易）
  大規模チーム → BLoC（テスト・分業が明確）
```
