# モジュール設計原則

モジュール分割と依存関係設計のための原則集。
設計判断の根拠として使用する。

---

## 凝集度（Cohesion）

**高い凝集度 = 良い設計**。
「このモジュールの要素は全て同じ理由で変化する」が理想。

### 凝集度レベル（高い順）

| レベル | 説明 | 例 |
|-------|------|---|
| 機能的凝集 | 単一の明確な機能を実行 | `UserAuthenticator`（認証のみ） |
| 順次的凝集 | 前の処理の出力を次が使う | データ変換パイプライン |
| 通信的凝集 | 同じデータセットを操作 | レポート生成（同一DBから） |
| 手順的凝集 | 特定の順序で実行 | ファイル処理の一連の手順 |
| 時間的凝集 | 同じタイミングで実行 | 初期化処理をまとめた `Bootstrapper` |
| 論理的凝集 | 「似ている」という理由だけ | `Utils` クラス ← 避けるべき |
| 偶発的凝集 | 全く関係ないものをまとめた | `MiscHelper` ← 絶対避ける |

**判定の問い**: 「このモジュールのある要素が変わる時、他の要素も必ず変わるか？」
- YES → 凝集度が高い
- NO → 分割を検討

---

## 結合度（Coupling）

**低い結合度 = 良い設計**。
「このモジュールを変更した時、他のモジュールへの影響が少ない」が理想。

### 結合度レベル（低い順 = 良い順）

| レベル | 説明 | 対策 |
|-------|------|------|
| データ結合 | 必要なデータのみを引数で渡す | 最良。これを目指す |
| スタンプ結合 | データ構造全体を渡す | 必要なフィールドのみに絞れるか検討 |
| 制御結合 | フラグで相手の動作を制御 | 別メソッドに分割する |
| 外部結合 | 共有の外部データ（グローバル変数等） | 依存性注入で解消 |
| 共通結合 | 共有のグローバル状態 | シングルトンの乱用を避ける |
| 内容結合 | 相手の内部実装に依存 | 最悪。プライベートな実装を参照している |

**判定の問い**: 「モジュールAを変更した時、モジュールBのコードを変えなければならないか？」
- 頻繁に YES → 結合度が高い → インターフェースの導入を検討

## 単一責任原則（SRP）

「クラス（モジュール）を変更する理由は1つだけであるべき」

### 責任とは何か

「責任 = 変化の理由（Actor）」。
1つのモジュールが複数の Actor（ユーザー・管理者・システム等）に奉仕している場合、責任が複数ある。

**例: SRP 違反**:
```
UserService
  - getUserProfile()       ← ユーザーが変更を要求
  - generateReport()       ← 管理者が変更を要求
  - sendWelcomeEmail()     ← マーケティングが変更を要求
```
3つの Actor に奉仕 → 分割すべき

**例: SRP 準拠**:
```
UserProfileRepository  ← ユーザープロフィールの読み書き
UserReportGenerator    ← レポート生成
UserEmailNotifier      ← メール通知
```

## 開放閉鎖原則（OCP）

「拡張に対して開いており、修正に対して閉じているべき」

新しいケースを追加するとき、既存コードを変更せず追加だけで対応できる状態が理想。

**典型的な OCP 違反**:
```swift
// 違反: 新しい支払い方法のたびに switch を修正する必要がある
func process(payment: Payment) {
    switch payment.type {
    case .creditCard: processCreditCard(payment)
    case .payPal: processPayPal(payment)
    // 新しい種別追加のたびにここを変更
    }
}
```

**OCP 準拠**:
```swift
// 準拠: 新しい支払い方法はプロトコルに準拠した新クラスを追加するだけ
protocol PaymentProcessor {
    func process(payment: Payment)
}
// 既存コードを変えず CreditCardProcessor, PayPalProcessor を追加
```

**判定の問い**: 「新しいバリエーションを追加するとき、既存ファイルを変更しているか？」
- YES → OCP 違反の疑い → ポリモーフィズムで代替できるか検討

## リスコフ置換原則（LSP）

「サブタイプはその基底型と置換可能であるべき」

基底クラスを受け取る関数にサブクラスを渡したとき、予期しない動作が起きてはならない。

**典型的な LSP 違反**:
```swift
// 違反: Rectangle を継承した Square が width 設定時に height も変えてしまう
// Square は Rectangle の「幅と高さは独立して設定できる」という契約を破っている
class Square: Rectangle {
    override func setWidth(_ w: Int) {
        super.setWidth(w)
        super.setHeight(w)  // 高さも変える → Rectangle の契約違反
    }
}
```

**実践的な対処**: 継承より合成（Composition over Inheritance）を使う。
サブクラスが基底クラスの「事前条件・事後条件・不変条件」を変えていないかを確認する。

**判定の問い**: 「このサブクラスを基底クラスの代わりに使ったとき、呼び出し側のコードを変えなければならないか？」
- YES → LSP 違反の疑い

## インターフェース分離原則（ISP）

「クライアントが使わないメソッドへの依存を強制しない」

大きなインターフェースを小さな役割ごとのインターフェースに分割する。

**典型的な ISP 違反と解消**:
```swift
// 違反: 読み取り専用クライアントも write メソッドの実装を強制される
protocol DataStore {
    func read(key: String) -> Data?
    func write(key: String, value: Data)  // 読み取り専用クライアントには不要
    func delete(key: String)              // 読み取り専用クライアントには不要
}

// 準拠: 役割ごとに小さなプロトコルに分割
protocol Readable {
    func read(key: String) -> Data?
}
protocol Writable {
    func write(key: String, value: Data)
    func delete(key: String)
}
// 読み取り専用クライアントは Readable のみ依存
```

**判定の問い**: 「このインターフェースの全メソッドを、全ての実装クラスが実際に使うか？」
- NO があれば → インターフェースを分割する候補

## 依存性逆転原則（DIP）

「高レベルのモジュールは低レベルのモジュールに依存してはならない。
どちらも抽象（インターフェース）に依存すべき」

### 具体例

**DIP 違反**:
```swift
class OrderService {
    private let db = MySQLDatabase()  // 具体的な実装に依存
    func createOrder(...) { db.save(...) }
}
```

**DIP 準拠**:
```swift
protocol OrderRepository {
    func save(order: Order)
}

class OrderService {
    private let repository: OrderRepository  // 抽象に依存
    init(repository: OrderRepository) { self.repository = repository }
}

class MySQLOrderRepository: OrderRepository {  // 具体的な実装
    func save(order: Order) { /* MySQL の実装 */ }
}
```

### DIP を適用すべき判断基準

適用すべき場合:
- 依存先が外部システム（DB・API・センサー）
- テスト時にモックが必要
- 依存先を差し替える可能性がある

**適用すべきでない場合（YAGNI）**:
- 依存先が安定した標準ライブラリ
- 差し替えの可能性がゼロに近い
- チームの規模から見てオーバーエンジニアリング

## パッケージ原則（大きなシステムのモジュール設計）

### 凝集性原則（どこに置くか）

- **REP（再利用・リリース等価原則）**: パッケージの粒度は再利用・リリースの粒度と等価
- **CCP（閉鎖性共通原則）**: 同じ理由で変化するクラスをまとめる（モジュールレベルの SRP）
- **CRP（全再利用原則）**: パッケージのクラスを全て使わないなら、そのパッケージに依存すべきでない

### 結合性原則（依存関係の設計）

- **ADP（非循環依存原則）**: パッケージの依存グラフに循環が存在してはならない
- **SDP（安定依存原則）**: 安定したパッケージに依存する（不安定→安定の方向）
- **SAP（安定抽象原則）**: 安定したパッケージは抽象的であるべき

---

## 循環依存の検出と解消

### 循環依存のパターン

```
A → B → C → A  ← 直接循環
A → B → A       ← 間接循環（1段）
```

### 解消方法

**方法1: 新しいパッケージの抽出**
```
A → B → C → A を分解して
A → B → C
↑          ↓
    D ← （共通の抽象）
```

**方法2: 依存性逆転**
```
A → B → C → A の C → A を
C → [InterfaceA] ← A に変更
（C は抽象に依存、A が実装）
```

**方法3: イベント駆動**
```
A → B → C → A の C → A を
C → [EventBus] → A に変更
（C はイベントを発行するだけ）
```

## 安定度の評価

モジュールの安定度 = (使う人の数) / (使う人 + 使われる人)

- **安定 = 多くから依存される**: 変更の影響が大きいため慎重に変える
- **不安定 = 少ししか依存されない**: 自由に変更できる

```
安定なモジュール（高安定度）:
  - 基本的なデータ型・値オブジェクト
  - 汎用ユーティリティ
  - インターフェース定義

不安定なモジュール（低安定度）:
  - UI コンポーネント
  - 特定機能のビジネスロジック
  - 外部API クライアント
```

**安定依存原則**: 不安定なモジュールが安定したモジュールに依存する。
逆（安定したモジュールが不安定なものに依存）は設計崩壊の原因。

## 境界コンテキスト（Bounded Context）

DDD（ドメイン駆動設計）の概念。
「同じ言葉が異なる意味を持つ領域ごとに境界を引く」

### 適用例

ECサイトの「User」:
- 注文管理コンテキスト: `Customer`（注文する人）
- 認証コンテキスト: `Account`（ログインする人）
- 配送コンテキスト: `Recipient`（受け取る人）

これらを1つの `User` クラスに詰め込むと肥大化する。
境界を引いてそれぞれの文脈で定義する。

### いつ境界コンテキストを使うか

- 「User という単語がコンテキストによって意味が違う」と感じた時
- モジュール間でデータ変換が頻繁に必要な時
- 異なるチームがそれぞれの領域を担当する時

**YAGNI**: 小さなアプリでは不要。まず 1 つのシンプルなモデルから始める。
