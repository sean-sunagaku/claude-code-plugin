# アーキテクチャパターン集

設計セッションで参照するアーキテクチャパターンの概要と適用基準。

---

## パターン選択の前提

どのパターンも「完璧」ではない。
**要件・チーム規模・スタック・スケジュール**に基づいて選択する。

選択基準:
1. 今の要件を満たすか
2. チームが理解・保守できるか
3. 採用スタックと相性が良いか
4. 変化への対応度（変わる可能性が高い部分を隔離できるか）

---

## 1. レイヤードアーキテクチャ（Layered Architecture）

```
Presentation Layer（UI・API エンドポイント）
         ↓
Application Layer（ユースケース・オーケストレーション）
         ↓
Domain Layer（ビジネスロジック・エンティティ）
         ↓
Infrastructure Layer（DB・外部API・ファイルシステム）
```

**適用基準**:
- シンプルな CRUD アプリ
- 小〜中規模チーム
- スタック: Spring Boot, Rails, Django, Laravel

**利点**:
- 理解しやすい・オンボードが早い
- 標準的な構造でドキュメントが豊富

**欠点**:
- ドメインロジックが薄い場合は過剰
- 循環依存が生まれやすい（特に Domain → Infrastructure）

**YAGNI チェック**: 単純な CRUD しかない → レイヤードで十分

---

## 2. クリーンアーキテクチャ（Clean Architecture）

```
[外側] UI・DB・外部API（詳細）
         ↓（依存方向は内側へ）
[中間] インターフェースアダプター
         ↓
[内側] ユースケース
         ↓
[最内] エンティティ（ビジネスルール）
```

**適用基準**:
- ドメインロジックが複雑
- UI や DB の差し替えが起こりうる
- 長期保守が前提

**利点**:
- テストが書きやすい（外部依存を切り離せる）
- UI・DB の変更がドメインロジックに影響しない

**欠点**:
- 学習コストが高い
- 小さなアプリには過剰
- ボイラープレートが多い

**YAGNI チェック**: DB を差し替える予定がない、UIが1種類だけ → 過剰かもしれない

---

## 3. ヘキサゴナルアーキテクチャ / ポート&アダプター

```
[外部] 入力アダプター（HTTP, CLI, Queue）
         ↓
      [ポート: in]
         ↓
    [アプリケーションコア]
         ↓
      [ポート: out]
         ↓
[外部] 出力アダプター（DB, 外部API, メール）
```

**適用基準**:
- 複数の入力チャンネル（HTTP + CLI + イベント等）
- テスト駆動開発を重視
- マイクロサービスの内部設計

**利点**:
- ポートを介してモック化が容易
- 外部依存の差し替えが明確

**欠点**:
- インターフェース定義が増える
- 入力が HTTP のみなら過剰

---

## 4. MVVM（Model-View-ViewModel）

```
View（UI表示・ユーザー操作の受け付け）
    ↕（バインディング）
ViewModel（UIロジック・状態管理・Viewへのデータ変換）
    ↕（プロトコル/インターフェース）
Model（ドメインロジック・データ取得）
```

**適用基準**:
- iOS（SwiftUI / UIKit）
- Android（Jetpack Compose）
- WPF / XAML 系
- 双方向バインディングが必要な UI

**利点**:
- UI のテストを ViewModel で代替できる
- iOS のエコシステムと相性が良い

**欠点**:
- ViewModel が肥大化しやすい（Massive ViewModel 問題）
- 状態管理が複雑な場合は TCA 等を検討

---

## 5. TCA（The Composable Architecture）

```
View → Action → Reducer → State → View（循環）
                    ↓
              Environment（副作用）
```

**適用基準**:
- iOS SwiftUI 専用
- 複雑な状態管理
- 副作用（非同期処理）が多い
- テスト・デバッグを重視

**利点**:
- 状態変化が追跡可能（Redux 的）
- テストが書きやすい
- 大規模チームでの一貫性

**欠点**:
- 学習コストが非常に高い
- 小さなアプリには圧倒的に過剰
- バージョン間の breaking changes が多い

**YAGNI チェック**: 状態管理が単純、チームに TCA 経験者がいない → MVVM + @Observable で始める

---

## 6. Feature-Sliced Design（FSD）

```
app/（グローバル設定・プロバイダー）
pages/（ページ・ルート）
widgets/（複合 UI ブロック）
features/（ユーザーアクション単位）
entities/（ビジネスエンティティ）
shared/（共通ユーティリティ）
```

**適用基準**:
- React / Next.js フロントエンド
- 中〜大規模アプリ
- 複数チームでの並行開発

**利点**:
- 機能の追加・削除が明確
- 上位レイヤーから下位レイヤーへの依存のみ許可（循環なし）

**欠点**:
- 慣れるまで「どのレイヤーに置くか」の判断が難しい
- 小規模プロジェクトには過剰

---

## 7. モノリス vs モジュラーモノリス vs マイクロサービス

| 構成 | 適用基準 | チーム規模 |
|------|---------|-----------|
| モノリス | スタートアップ・MVP・小規模 | 〜5人 |
| モジュラーモノリス | 中規模・将来の分割を考慮 | 5〜20人 |
| マイクロサービス | 大規模・独立デプロイが必須 | 20人〜 |

**YAGNI 警告**: マイクロサービスは「いつか必要になるかも」では選ばない。
今の要件でモノリスが機能する場合、モノリスが正解。

## マイナー・ニッチなパターン（10案列挙の際に参考にする）

10案を網羅的に列挙する際、メジャーなパターンだけでは偏るため、以下も候補に含める。

| パターン名 | 概要 | 適した状況 |
|-----------|------|-----------|
| **EBI（Entity-Boundary-Interactor）** | Clean Architecture の原型。Entity・Boundary・Interactor の3要素で構成 | DDD 的アプローチを軽量に取りたい場合 |
| **PAC（Presentation-Abstraction-Control）** | 複数の協調エージェント（PAC トリプレット）が階層的に構成 | 複雑な UI 状態が複数存在する場合 |
| **Pipes & Filters** | データが一連のフィルター（変換器）を順番に通過する | データ変換パイプライン・ストリーム処理 |
| **CQRS（Command Query Responsibility Segregation）** | 読み取り（Query）と書き込み（Command）のモデルを分離 | 読み書きの頻度・スケール要件が異なる場合 |
| **Event Sourcing** | 状態変化をイベントの列として記録し、現在状態を再構築する | 履歴・監査が重要な場合・undo機能が必要な場合 |
| **Event-Driven Architecture** | コンポーネント間をイベントで疎結合にする | 非同期処理・マイクロサービス間通信 |
| **Micro Frontends** | フロントエンドを独立してデプロイできる小さな UI に分割 | 複数チームが独立して開発・デプロイする場合 |
| **Modular Monolith** | モジュール境界を明確に定義した上で1つのプロセスとして動かすモノリス | マイクロサービスへの将来的な移行を見据えつつ、今はシンプルに |
| **Active Record** | モデルがデータアクセスロジックを内包する（Rails 等のデフォルト） | 小規模・CRUD 中心・速度優先 |
| **Repository + Service Layer** | Repository でデータアクセスを抽象化し、Service でユースケースを実装 | Layered の変形として最も一般的な中規模構成 |
| **Flux / Redux** | 単方向データフロー。Action → Dispatcher → Store → View | React フロントエンドの状態管理 |
| **Vertical Slice Architecture** | 機能単位（スライス）で全レイヤーを束ねる。水平レイヤーでなく垂直に分割 | 機能追加を独立に進めたい場合 |

## パターン選択フローチャート

```
アプリの規模・複雑さは？
├── 小さい（数画面・CRUD中心）
│   └── シンプルなレイヤード or MVVM
├── 中程度（複数機能・チーム複数人）
│   ├── iOS → MVVM + Repository / TCA（経験者がいる場合）
│   ├── React → Feature-Sliced Design
│   └── バックエンド → レイヤード or ヘキサゴナル
└── 大きい（複数チーム・差し替え要件あり）
    ├── iOS → TCA / Clean Architecture
    ├── React → FSD + マイクロフロントエンド
    └── バックエンド → クリーンアーキテクチャ / ヘキサゴナル
```

---

## 混合パターンについて

現実のプロジェクトでは複数パターンを組み合わせることがある:
- MVVM（UIレイヤー）+ Repository Pattern（データレイヤー）
- Clean Architecture（コア）+ レイヤード（外側）

混合する場合は「どこでパターンが切り替わるか」を明確にする。
混在のルールが明確でないと設計が崩壊する。
