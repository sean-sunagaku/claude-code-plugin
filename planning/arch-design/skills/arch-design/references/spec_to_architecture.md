# 仕様書からアーキテクチャへの変換手法

仕様書・要件定義を入力として、アーキテクチャ設計に変換するための手法集。
Step 1（コンテキスト把握）と Step 2（パターン選択）で使用する。

---

## 変換の実践フロー

```
1. 仕様書を読みユビキタス言語を抽出する
   → ドメイン用語の一覧（同じ言葉が異なる意味を持つ箇所を特定）

2. ユースケースを列挙する
   → 「誰が」「何をする」「結果はどうなる」の形式で一覧化

3. Bounded Context を特定する
   → 言語の意味が変わる境界を引く

4. C4 Context レベルから設計する
   → 全体像を把握（システムが何をするか、誰と通信するか）

5. モジュール分割の判断
   → Common Closure Principle: 同じ理由で変わるものを同じモジュールへ

6. 依存方向を設計する
   → ドメインが最も安定、インフラが最も不安定

7. インターフェースを Contract-First で定義する
   → 実装前に API を確定

8. プラットフォームに合ったパターンを選ぶ
   → iOS→TCA/MVVM, Web→App Router + FSD, etc.

9. YAGNI でフィルタリングする
   → 今必要でない設計要素を削除

10. 3の法則で抽象化タイミングを制御する
    → 重複が3回出るまで待つ
```

---

## C4 Model — アーキテクチャの可視化

**概要**: システムを4つの抽象レベル（Context, Container, Component, Code）で可視化するモデル。
設計手法ではなく「コミュニケーション・ドキュメント作成」のためのツール。

### 4つのレベル

| レベル | 対象 | 使う場面 |
|-------|------|---------|
| **Context** | システム全体と外部アクター・外部システムの関係 | 非技術者への説明、スコープの確認 |
| **Container** | 実行可能な単位（アプリ、サービス、DB）の構成 | 技術的な全体像の把握 |
| **Component** | Container 内のモジュール・コンポーネント | モジュール設計の議論 |
| **Code** | クラス・関数レベルの詳細 | 実装詳細（通常は自動生成） |

### Step 1 での活用

仕様書を読んだ後、**Context 図を脳内で描く**:
- このシステムを使う人間（アクター）は誰か
- 連携する外部システムは何か
- システムの境界（スコープ）はどこか

**チェックリスト**:
- [ ] システム外部の人間・システムとの関係が描けているか
- [ ] 技術的な境界（サービス・DB・アプリ）が明確か
- [ ] モジュール間の責任が明確に分離されているか

## ドメイン駆動設計（DDD）

**いつ使うべきか**: ビジネスロジックが複雑で、ドメインエキスパートとの密な協働が必要なとき。
**いつ使うべきでないか**: ドメインが単純（CRUD メイン）なとき、ドメインエキスパートが不在のとき。

### Event Storming（仕様書から始める場合の代替手法）

ドメインイベントを洗い出してモジュールを発見する手法:

```
1. ドメインイベントを列挙する（オレンジ付箋）
   例: 「注文が確定された」「ユーザーが登録した」「支払いが完了した」
   ルール: 過去形・受動態で書く

2. コマンド（イベントの原因）を特定する（青付箋）
   例: 「注文を確定する」「ユーザーを登録する」

3. アクター（コマンドを実行する人・システム）を特定する
   例: 「顧客」「管理者」「決済システム」

4. Aggregate（整合性の境界）を特定する（黄色付箋）
   例: 「注文」「ユーザー」「在庫」

5. Bounded Context を引く
   → 同じ言葉が異なる意味を持つ境界を見つける
```

### Bounded Context の実践

「User」という言葉が複数の意味を持つ典型例:

| コンテキスト | 呼び方 | 関心事 |
|-----------|------|-------|
| 認証 | `Account` | ログイン情報・パスワード |
| 注文管理 | `Customer` | 注文履歴・住所 |
| 配送 | `Recipient` | 配送先・受取状況 |

これらを1つの `User` クラスに詰め込むと肥大化する。
コンテキストごとに別のモデルとして定義する。

**チェックリスト**:
- [ ] 仕様書内で同じ言葉が異なる意味で使われている箇所がないか
- [ ] 各コンテキストのモデルが他のコンテキストに依存していないか
- [ ] コンテキスト間の通信が明示されているか（Context Map）

### Context Map（コンテキスト間の関係）

| 関係パターン | 説明 | 使う場面 |
|-----------|------|---------|
| **Shared Kernel** | 2コンテキストが同一のモデルを共有 | 密結合を許容できる場合（変更時に両側への影響あり） |
| **Customer-Supplier** | Supplier が Consumer のニーズに応じてモデルを提供 | 上流・下流の関係が明確な場合 |
| **Anti-Corruption Layer** | 外部コンテキストのモデルを自コンテキストの言語に変換する層 | 外部システム・レガシーとの統合 |
| **Open Host Service** | 公開APIとして外部に提供 | 多数のクライアントが利用する場合 |

## ユースケース駆動設計

**概要**: 仕様書のユースケース（誰が何をするか）からモジュールを導出するアプローチ。
DDD が難しい場合や仕様書がユースケース形式の場合に有効。

### プロセス

```
1. ユースケース一覧を作成する
   形式: 「[アクター] が [アクション] すると [結果]」
   例:
   - ユーザーが「注文確定」ボタンを押すと注文が作成される
   - 管理者が在庫を更新すると通知が送られる

2. ユースケースをグルーピングしてモジュール境界を引く
   → 同じアクターが使うユースケースをまとめる
   → 同じデータを扱うユースケースをまとめる

3. 各ユースケースを UseCase クラス/関数として実装する
   例: CreateOrder, UpdateInventory, SendNotification
```

**チェックリスト**:
- [ ] 1つのユースケースが1つのクラス/関数に対応しているか
- [ ] ユースケース間の共通ロジックが適切に分離されているか（過早な共通化に注意）
- [ ] ユースケース名がビジネスの言葉（ドメイン用語）になっているか

## Contract-First インターフェース設計

**概要**: 実装の前にインターフェース（契約）を定義するアプローチ。
「呼び出し側が必要とするもの」から設計するため、依存性逆転と相性が良い。

### プロセス

```
1. 呼び出し側（クライアント）が必要とするメソッドを先に定義する
   例:
   protocol OrderRepository {
     func findById(id: OrderID) async throws -> Order
     func save(order: Order) async throws
   }

2. 実装を後から追加する
   class SQLiteOrderRepository: OrderRepository {
     // 具体的な実装
   }

3. テストダブル（モック）を作成できることを確認する
   class MockOrderRepository: OrderRepository {
     // テスト用の実装
   }
```

**利点**:
- 並行開発が可能（インターフェースが確定すれば実装とクライアントを並行開発できる）
- テストダブルが早期に作れる
- 「何が必要か」を明確にしてから「どう実装するか」を考えられる

**チェックリスト**:
- [ ] インターフェースは「クライアントが本当に必要とするメソッドのみ」を持っているか
- [ ] インターフェース名がドメインの言語で表現されているか（技術詳細でなく）
- [ ] Protocol/Interface に具体的な実装の詳細（SQL、HTTP 等）が漏れていないか

## 仕様書の読み方：設計につながる情報の抽出

### 抽出すべき情報

```
機能要件の読み方:
- 名詞 → エンティティ・集約の候補
- 動詞 → ユースケース・コマンドの候補
- 「〜の場合」「〜したとき」 → ドメインイベント・条件分岐の候補
- 「〜できる」「〜できない」 → 権限・制約・ビジネスルール

非機能要件の読み方:
- 「〜以内に応答する」→ パフォーマンス要件 → キャッシュ・非同期処理の検討
- 「〜万ユーザーまで対応」→ スケーラビリティ → データストア設計・スケール戦略
- 「〜を変更できる」→ 可変性 → 抽象化・設定外部化の検討
- 「〜に対応する予定」→ 将来要件 → YAGNI でフィルタ（本当に今必要か？）
```

### 曖昧な仕様の扱い

設計中に仕様の不明点が生じた場合:
1. 不明点を記録する
2. 設計への影響を評価する（高/中/低）
3. 影響が高い場合はユーザーに質問する（[ASK_USER_REQUEST] プロトコルを使用）
4. 影響が低い場合は最もシンプルな仮定で進め、ADR に「仮定」として記録する
