# ステップ詳細

各ステップの詳細フロー、担当エージェント、完了条件を定義する。

---

## Step 1: 仕様・コンテキストの把握

**目的**: 設計に必要な情報をすべて明確化する

**担当**:
- Facilitator（主導）
- Architecture Lead（分析・質問）

**フロー**:

```
1. Facilitator がドキュメントを検索・読み込み
   - Glob で docs/, spec/, .claude/ を探す
   - README.md, 仕様書, 要件定義書を Read

2. Architecture Lead がコンテキスト分析
   - 機能要件を抽出
   - 非機能要件を抽出（パフォーマンス・スケーラビリティ・保守性等）
   - 技術スタックを特定
   - 制約条件を特定（チーム・スケジュール・既存コード等）

3. 不明点がある場合
   - Architecture Lead → Facilitator: 質問リクエスト
   - Facilitator → AskUserQuestion でユーザーに確認
   - 回答をチームに共有

4. Platform Expert が技術スタックを詳細確認
   - package.json / pubspec.yaml / Package.swift 等を Read
   - ライブラリバージョンを確認
```

**完了条件**:
- [ ] 機能要件が一覧化されている
- [ ] 非機能要件（明示的・暗黙的）が確認されている
- [ ] 技術スタック（言語・フレームワーク・主要ライブラリ）が確定
- [ ] 既存コードのアーキテクチャ（あれば）が把握されている
- [ ] `step1-context/` ディレクトリに成果物が配置されている

**成果物ディレクトリ** (`step1-context/`):
- `README.md` — 機能要件・非機能要件・制約・状態遷移・設計キーポイント
- `module-designer-feedback.md` — モジュール設計観点の論点
- `dependency-analyst-feedback.md` — 依存関係分析・循環依存リスク
- `devils-advocate-feedback.md` — YAGNI 警告・本当に重要な技術課題
- `platform-expert-feedback.md` — スタック適合性・設計提言・フレームワーク制約

## Step 2: アーキテクチャ案の網羅的列挙・比較・選定

**目的**: 10個の候補案を網羅的に列挙し、多軸スコアリングで比較後、1案を選定する

**担当**:
- Architecture Lead（主導・列挙・スコアリング・最終提案）
- Platform Expert（スタック適合性スコア担当）
- Devil's Advocate（複雑性・YAGNI スコア担当）
- Module Designer・Dependency Analyst（聴講・フィードバック）

**フロー**:

```
Phase 2a: 10案の網羅的列挙（Architecture Lead 主導）
  - references/architecture_patterns.md を起点に候補を列挙
  - メジャーなパターンだけでなくマイナー・ニッチなパターンも含める
  - 各案に1文の概要を付ける（詳細評価は次フェーズ）
  - broadcast でチーム全体に共有

Phase 2b: 多軸スコアリング（全エージェント参加）
  - 5軸・各1-5点でスコアリング（下記スコアリング基準を参照）
  - Platform Expert → スタック適合性・学習コスト軸
  - Devil's Advocate → 複雑性・YAGNI スコア軸
  - Architecture Lead → 保守性・テスト容易性軸
  - 結果を比較表にまとめる

Phase 2c: Top 2-3 への絞り込み（全員議論）
  - 合計スコア上位 + 議論で注目案を Top 2-3 に絞る
  - 各案の詳細なメリット・デメリットを議論
  - Devil's Advocate が上位案の過剰複雑化を批判
  - ユーザーに Top 2-3 を提示し、方向性を確認

Phase 2d: 1案の選定（ユーザー選択・CRITICAL）
  - Facilitator が AskUserQuestion で Top 2-3 を提示し、ユーザーにパターンを選んでもらう
  - 各選択肢に preview でディレクトリ構成とアーキテクチャ図を表示
  - 推奨案を第一選択肢に配置（「推奨」ラベル付き）
  - ユーザーの選択が確定してから Step 3 に進む（暗黙的に進めない）
  - 選択理由を ADR 形式で記録
```

**スコアリング基準（5軸、各 1-5 点）**:

| 評価軸 | 説明 | 主な評価者 |
|--------|------|----------|
| 保守性・拡張性 | 変更・追加への対応容易さ | Architecture Lead |
| テスト容易性 | ユニットテスト・統合テストの書きやすさ | Architecture Lead |
| スタック適合性 | 採用フレームワーク・ライブラリとの相性 | Platform Expert |
| 学習コスト | チームがパターンを習得・保守できるか | Platform Expert |
| シンプルさ（反転） | 複雑すぎない・YAGNI 違反でない（高 = シンプル） | Devil's Advocate |

**完了条件**:
- [ ] 10個以上の候補案が列挙されている（マイナー案を含む）
- [ ] 全候補の比較表（スコアリング含む）が作成されている
- [ ] Top 2-3 への絞り込み経緯が記録されている
- [ ] アーキテクチャパターンが1つに選定されている
- [ ] 採用理由・棄却理由が記録されている
- [ ] `step2-pattern-comparison/` ディレクトリに成果物が配置されている

**成果物ディレクトリ** (`step2-pattern-comparison/`):
- `README.md` — 10案比較表・Top 3 サマリー・棄却理由
- `scoring-rationale.md` — Top 3 詳細スコア根拠・エージェント間合意事項
- `implementation-details.md` — 確定実装方式・依存マップ・コード例
- `patterns/` — 各案の詳細設計図（アーキテクチャ図・ディレクトリ構成・メリデメ）
  - `01-<pattern>/README.md` 〜 `10-<pattern>/README.md`

## Step 3: モジュール設計・依存関係定義

**目的**: 採用パターンに基づき、具体的なモジュール境界・インターフェース・依存関係を確定

**担当**:
- Module Designer（主導・モジュール分割）
- Dependency Analyst（主導・依存関係設計）
- Devil's Advocate（過剰分割・過剰抽象化への批判）
- Architecture Lead（全体一貫性の監督）

**フロー**:

```
Round 1（並列議論）:
  Module Designer → モジュール分割提案
  Dependency Analyst → 依存方向の設計

Round 2（クロスレビュー）:
  各エージェントが相互にフィードバック
  Devil's Advocate が批判レポートを提出

Round 3（収束）:
  Architecture Lead が整合性を確認
  修正が必要な場合は Round 2 に戻る
  合意が得られたら確定
```

**完了条件**:
- [ ] 全モジュールの名前・責務が確定
- [ ] 各モジュールの公開インターフェースが定義済み
- [ ] 依存方向が図示されている
- [ ] 循環依存がない
- [ ] `3_modules.md` が作成されている

## Step 4: 設計書出力・ユーザー承認

**目的**: 最終アーキテクチャ設計書を生成し、ユーザーに提示・承認を得る

**担当**:
- Architecture Lead（設計書ドラフト）
- Facilitator（出力・ユーザー提示）

**フロー**:

```
1. Architecture Lead が全議論を統合
   - 1_context.md + 2_pattern.md + 3_modules.md を参照
   - 不整合があれば修正

2. Facilitator が設計書を Write で出力
   - 4_architecture.md を作成
   - references/output_templates.md のテンプレートを使用

3. ユーザーへの提示
   - 設計書の概要を表示
   - 重要な設計決定事項を強調
   - 承認 or フィードバックを求める

4. フィードバックがあれば修正
   - 軽微な修正: Facilitator が直接対応
   - 大きな方針変更: 該当ステップに戻って再議論

5. 承認されたら session.json を completed に更新
```

**完了条件**:
- [ ] `4_architecture.md` が作成されている
- [ ] 全モジュールとその依存関係が設計書に含まれている
- [ ] ADR（主要な設計決定の記録）が含まれている
- [ ] ユーザーの承認が得られている

## ユーザーへの質問プロトコル

設計中に不明点が生じた場合のエスカレーション:

```
エージェント → Facilitator への質問フォーマット:
[ASK_USER_REQUEST]
質問: [ユーザーに聞きたいこと]
背景: [なぜこの情報が設計に必要か]
選択肢（あれば）:
- A: [選択肢A] → [設計への影響]
- B: [選択肢B] → [設計への影響]
緊急度: 高/中/低
依頼元: [エージェント名]
```

Facilitator は受け取った質問を整理し、AskUserQuestion でユーザーに確認する。
回答は全エージェントに broadcast で共有する。
